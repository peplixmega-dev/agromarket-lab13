# Лабораторная 13 · Заказы

В версии 1.1.0 доступна розничная покупка с доставкой. Для демонстрации откройте start-demo.command, зарегистрируйте покупателя, добавьте в корзину две позиции, обновите страницу, введите адрес и оформите заказ. На странице «Мои заказы» отображаются позиции и сумма. Отмена нового заказа возвращает товары на склад. Для просмотра входящих позиций войдите демо-продавцом, указанным в корневом README.

| Запрос | Результат |
|---|---|
| POST /api/orders | Принимает items с productId и quantity, а также address. Возвращает 201, номер, сумму и позиции. |
| GET /api/orders/my | История текущего покупателя с ценами на момент оформления. |
| POST /api/orders/:id/cancel | Отмена своего нового заказа. Для чужого или отсутствующего заказа возвращает 404, при повторной отмене — 409. |
| GET /api/orders/incoming | Продавец видит позиции своих товаров, имя покупателя и адрес доставки. |
| PATCH /api/products/:id | Продавец может изменить stock у своего товара. При создании товара владельца определяет сервер. |

В этой версии проекта роль продавца называется admin. Покупки хранятся в purchase_orders и order_items, оптовые заявки из ЛР7 по-прежнему используют orders. Новый клиент отправляет items и address, прежняя форма отправляет данные оптовой заявки. В БД суммы в тенге хранятся как целые числа, для общей суммы используется bigint.

## Как проверить

- `npm run demo` или `npm run dev` из корня поднимает демосайт с временной базой и каталогом на http://localhost:3000. Товары демобазы имеют остаток 20.
- `npm run test:server` запускает серверный набор. При установленных серверных утилитах PostgreSQL скрипт поднимает отдельный временный экземпляр. В среде только с PGlite многосессионная проверка пропускается с явным сообщением. CI использует PostgreSQL.
- `npm run test:run`, `npm run coverage`, `npm --prefix client run lint`, `npm --prefix client run build` проверяют React.
- `npm run e2e` запускает сценарии Chromium на отдельной локальной базе. `BASE_URL=https://<домен> npm run e2e:smoke` выбирает три проверки чтения: каталог, товар и корзина.
- [Коллекция Postman](../postman/AgroMarket.postman_collection.json) последовательно проверяет запросы на свежей демобазе. В полном архиве также лежат HTML-отчёт Playwright, отчёт покрытия и учебные трассы ЛР10–12.

## Миграция и результаты

Из каталога server выполните `npm run db:migrate` с DATABASE_URL целевой базы. Команда подготавливает базовую схему и применяет db/migrations/013_orders.sql. Для отдельного SQL-файла есть `node scripts/migrate.js db/migrations/013_orders.sql`. Проверка дважды применяет миграцию к образцу прежней базы и сверяет сохранённые товары и заявки. На действующей базе новый stock равен нулю. Продавец указывает реальные остатки через форму.

## Ответы для защиты

1. **Транзакция.** Оформление включает создание заказа, запись позиций и списание запасов. Атомарность объединяет эти действия, изоляция согласует параллельные покупки, ограничения поддерживают согласованность, зафиксированные изменения переживают перезапуск PostgreSQL.
2. **Сбой до COMMIT.** При закрытии соединения PostgreSQL откатит незавершённую транзакцию. При записи отдельными автокоммитами в базе мог бы остаться заказ без позиций или с частичным списанием.
3. **Соединение.** BEGIN и все следующие операции должны попасть в одну сессию, поэтому код получает client из пула. В finally он вызывает release. Если забыть release, новые запросы со временем начнут ждать свободного соединения.
4. **Последняя единица.** Тест ставит блокировку и дожидается двух запросов в очереди настоящего PostgreSQL. Первый покупатель получает 201. После освобождения строки второй видит остаток ноль и получает 409 с available: 0. В базе ровно одна покупка. Сортировка по id задаёт одинаковый порядок захвата строк для многопозиционных заказов.
5. **Отрицательный контроль.** На временной SQL-фикстуре EXPLAIN показал LockRows при блокирующем чтении и отсутствие этого узла в контрольном запросе. Проверка наличия узла дала PASS и FAIL соответственно. HTTP-коды для варианта API без блокировки не измерялись. CHECK(stock >= 0) защищает данные в момент записи. Чтобы покупатель получил осмысленный ответ о доступном количестве, запас проверяется под блокировкой.
6. **Сумма.** Клиент может изменить localStorage и тело запроса. Сервер принимает идентификаторы и количество, читает цены из базы и рассчитывает итог сам. Входная схема ограничивает поля, которые клиент вправе задавать.
7. **Цена позиции.** Если цена товара завтра изменится, сумма вчерашнего заказа останется прежней. Для расширенного чека можно также фиксировать название и единицу измерения на момент продажи.
8. **Доступ.** При отмене поиск включает buyer_id из токена. Одинаковый 404 для чужого и отсутствующего заказа исключает раскрытие факта покупки. Во входящих продавец видит адрес, имя и свои позиции для исполнения доставки.
9. **Удаление товара.** Внешний ключ сохраняет связь между товаром и историей заказов. API сообщает о конфликте. Если потребуется снятие с продажи, можно добавить признак archived и скрывать такие позиции из каталога.
10. **Миграция.** Файл SQL находится в системе контроля версий. Одни и те же изменения можно применить в разработке, CI и Neon. Повторяемость позволяет безопасно восстановиться после прерванного выпуска.
11. **Порядок релиза.** Сначала применяется совместимая миграция, затем разворачивается API и клиент. При откате старый код работает с привычными таблицами. Удаление или переименование используемой колонки требует отдельного переходного выпуска.
12. **Корзина.** localStorage сохраняет гостевую корзину при перезагрузке и обходится без серверной сессии. На другом устройстве будет отдельная корзина. При оформлении сервер перепроверяет доступность и цены.
13. **Версия.** 1.1.0 добавляет новую возможность с совместимостью прежних форм и маршрутов. Патч подходит для исправления. Изменение действующего контракта без переходного периода потребовало бы новой основной версии.
