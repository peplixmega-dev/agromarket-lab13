# Лабораторная 12 — тестирование фронтенда

Работа продолжает ЛР10–11. Сервер и клиент находятся в одном репозитории.
Рабочая папка пока называется `lab11chickengun-main`; компактный архив —
`lab12chickengun-source.zip`, внутри него папка `lab12chickengun-main`.

## Запуск сайта и тестов

На этом Mac:

- `start-demo.command` → открыть http://localhost:3000. Терминал оставить открытым.
- `start-tests.command` → серверные тесты, покрытие React, lint и полный локальный E2E.
- Демоадминистратор: `admin@agromarket.kz` / `DemoAdmin12345!`.
  Это учётная запись исключительно временной демобазы; после остановки данные сбросятся.

После распаковки компактного архива нужны Node.js 22.22.2+ (ветка 22) или 24.15+
(ветка 24) и npm. Из корня:

```bash
npm run setup
cd client
npx playwright install chromium
cd ..
npm run demo
```

Команды из `client/`:

```bash
npm test                   # один прогон, совместимость с ЛР10–11
npm run test:run            # такой же прогон, команда из ЛР12
npm run test:watch          # интерактивный перезапуск
npm run coverage           # HTML: coverage/index.html
npm run lint
npm run build
npm run e2e                # весь локальный набор, API запускается автоматически
npm run e2e:smoke          # только 2 smoke-сценария на локальной временной среде
npm run e2e:report         # последний HTML-отчёт
npx playwright test --ui
```

В корне также доступны `npm run test:run`, `npm run coverage`, `npm run e2e`,
`npm run e2e:smoke` и `npm run test:server` (изолированный серверный набор).
Внутри `server/` обычный `npm test` требует отдельную PostgreSQL `agromarket_test`,
а `npm run test:local` сам создаёт PGlite. GitHub CI использует PostgreSQL 17.

## Что добавлено

- MSW **2.x**, совместимая с API `http`, `HttpResponse`, `setupServer`, `onUnhandledRequest`
  из задания. Версия закреплена диапазоном ^2; миграция на MSW 3 требует изменения API.
- `src/test/handlers.js`: ответы в реальном формате API (массив products, объект user/token,
  ошибки error/details). Роль обычного покупателя здесь `user`, продавца — `admin`.
- `src/test/server.js`: setupServer; в setup — error для необработанного запроса,
  cleanup, resetHandlers, очистка событий, моков, localStorage и URL после каждого теста.
- Прямые подмены глобального fetch удалены. `vi.fn()` используется для обработчиков
  событий и подсчёта сетевых обработчиков; apiFetch и fetch остаются настоящими.
- Помощник `renderWithProviders` настраивает URL перед render. React Router и AuthContext
  в проекте отсутствуют, поэтому лишние провайдеры не добавлены: ссылки — обычные `<a>`,
  а App выбирает страницу по pathname. Переходы и перезагрузка проверяются браузером.
- Карточка ведёт на `/products/:id`; страница показывает товар, единицу измерения,
  загрузку и 404/500. Vercel rewrites и локальный fallback обеспечивают прямые ссылки.
- Администратор может удалить товар с подтверждением. Ошибка удаления видна в карточке.
- Цена -500 получает понятный текст в форме; запрос блокируется браузером и дополнительной
  проверкой submit. При обходе формы Zod возвращает 400 с details.price.

У товаров нет stock: отсутствие на складе не имитируется. Поле unit есть и проверяется.

## Полные E2E и smoke

**Полные E2E запускаются только локально**, на автоматически созданной базе PGlite в памяти.
Playwright собирает React и запускает настоящий Express на 127.0.0.1:3100, БД — порт 55440.
Существующая DATABASE_URL не используется. `reuseExistingServer: false` не позволяет
случайно проверить чужой уже запущенный API. После окончания база уничтожается.

Учётная запись продавца соответствует `admin` этого проекта: добавлять новую роль farmer
и ослаблять права API ради названия из примера не нужно. Playwright передаёт сиду
`E2E_ADMIN_EMAIL`/`E2E_ADMIN_PASSWORD` через окружение; пароль по умолчанию генерируется
на каждый запуск. При желании задать свои **локальные тестовые** значения в `.env.e2e`
по примеру `.env.e2e.example`. Пароль не записывается в тесты и не печатается в лог демосервера.
Для smoke учётные данные не нужны.

Полный набор: два smoke-сценария; прямая ссылка входа; регистрация → выход → повторный
вход → перезагрузка → заявка; запрет админки гостю; неверный пароль; создание/удаление
товара администратором; отрицательная цена (браузер и реальный API). Итого **8**.
Созданный товар удаляется через UI в `finally`; чужие товары не выбираются для удаления.
Уникальные имена и email используют UUID. Лимит авторизации ЛР11 остаётся включённым,
каждый полный запуск получает новый сервер и новый счётчик, workers = 1.

На внешнем сайте разрешено только чтение:

```bash
BASE_URL=https://your-site.vercel.app npm run e2e:smoke
# PowerShell:
# $env:BASE_URL="https://your-site.vercel.app"; npm run e2e:smoke
```

Поддерживаются прежние E2E_BASE_URL и PRODUCTION_URL. Любой из этих URL ограничивает
`testMatch` файлом `catalog.spec.js`, даже если случайно запустить `npm run e2e`.
Дополнительно тесты записи имеют запрет запуска при внешнем URL, а smoke блокирует
сетевые методы, кроме GET/HEAD/OPTIONS. `e2e:prod` требует HTTPS URL и запускает только smoke.
Проверено через `BASE_URL=https://example.invalid npm run e2e -- --list`: ровно два smoke,
без сетевого обращения к example.invalid.

Существующие CI/schedule из ЛР10 обновлены: workflow **Smoke (production)** теперь выполняет
только чтение по кнопке и ежедневно в 09:00 Asia/Almaty. Variable `PRODUCTION_URL` остаётся
той же. Таймаут 90 секунд учитывает холодный старт API; trace и screenshot сохраняются
при падении. Полного E2E против продакшена больше нет.

Измерения 13 ноября 2026, Node.js 24.22.1, Chromium. Это длительности из отчётов одного
локального прогона, а не гарантированная скорость.

| Уровень | Что проверяется | Количество | Время |
|---|---|---:|---:|
| Сервер: Vitest + Supertest | Express, JWT, SQL, Zod, роли, CORS, rate limit | 51 | 3,47 с |
| Компоненты: Vitest + RTL + MSW | карточки, каталог, сессия, формы, ошибки API, страница товара | 40 | 3,16 с |
| E2E: локальный Playwright | настоящий браузер → React → Express → PGlite | 8 | 7,1 с |
| Smoke: продакшен | каталог и переход на товар, только чтение | 2 подготовлены | не запускался, нет URL |

Два smoke также прошли в составе локальных 8 E2E. Эти локальные результаты не являются
проверкой Vercel. Время E2E включает запуск демосреды. Покрытие строк React — **95,97%**
(191 из 199), порог CI остаётся 60%. Минимум покрыт AdminOrders.jsx (68,75%): кнопка
ручного обновления списка заявок пока не покрыта отдельным компонентным тестом.
Lint и сборка прошли. Старые серверные 51 проверки сохранены.

## CI и сдача

В корневом `.github/workflows/ci.yml` job `build`: npm ci → production audit → lint →
`npm run test:run` → coverage → build. Серверный job `test` сохранён.
Полные E2E выполняются локально; отдельный workflow production выполняет только smoke.

В GitHub нужно: перенести изменения в полный Git-клон; PR `test/frontend` с ревью напарника;
сделать `test` и `build` обязательными для main; проверить зелёный Actions. Затем создать
отдельный PR с временно сломанным тестом, убедиться в запрете merge и закрыть без слияния.
Ограничение YAML само не настраивает. В текущей папке нет .git и подключённого продакшена,
поэтому PR, защита main, скриншот Actions и smoke Vercel здесь не выполнены и не заявлены.

## Лабораторная 12 — ответы и защита

1. **Какие недоделки нашли.** В карточке не было ссылки и самой страницы товара;
   нельзя было удалить созданный товар через UI; при отрицательной цене браузер блокировал
   отправку без постоянного текстового сообщения в форме. Эти сценарии добавлены.
   Состояния загрузки/ошибок, label и обработка 401/429/400 были сделаны в ЛР10–11 и теперь
   проверяются через MSW. Повторный клик при ожидании входа не отправляет второй запрос.
2. **MSW вместо vi.mock(fetch).** Обработчики перехватывают запрос по HTTP-методу и URL.
   Компонент, apiFetch, сериализация и заголовки продолжают работать. В одном тесте можно
   независимо задать ответы каталога, профиля и заявки. Неверный URL выдаёт необработанный
   запрос. Мок должен совпадать с контрактом API; иначе тест проверяет несуществующую ситуацию.
3. **Изоляция.** resetHandlers убирает переопределения server.use, cleanup размонтирует React,
   localStorage.clear удаляет токен. Без этого порядок запуска влияет на результаты:
   например, следующий тест получает прежний 500 или чужую авторизацию.
4. **Пирамида и jsdom.** Быстрых компонентных проверок много, полных E2E мало: они медленнее
   и зависят от браузера/БД. jsdom реализует DOM в Node, но не полноценную отрисовку,
   геометрию и CSS браузера. Поэтому unit-тесты не доказывают правильность внешнего вида.
5. **Поиск элементов.** Role/label отражают интерфейс пользователя и доступность, классы
   описывают оформление. getBy требует элемент сразу; queryBy удобен для отсутствия;
   findBy ждёт асинхронного появления. within сужает поиск конкретной формой/карточкой.
6. **Автоожидание.** Playwright ждёт готовности элемента и повторяет expect. Фиксированный
   waitForTimeout добавляет задержку и всё равно нестабилен на медленном CI. В сценариях
   используются expect, события response и состояния интерфейса, без sleep.
7. **Уникальный email.** UUID предотвращает конфликт 409 при повторных регистрациях;
   Date.now также снижает риск, но UUID удобнее при параллельных запусках.
8. **Продакшен.** Полный E2E создаёт пользователей/товары/заявки, поэтому использует отдельную
   локальную БД. Smoke только читает каталог и товар и допустим после деплоя Vercel.
   Он обнаруживает ошибки URL API, CORS и доступности, которые изолированные моки не видят.
9. **Цена -500.** Первый E2E показывает браузерный rangeUnderflow и текст UI, POST отсутствует.
   Второй шаг обходит HTML-форму настоящим fetch: сервер отвечает 400 с details.price.
   Нужны оба уровня: удобство пользователя и защита от запроса в обход браузера.
   Компонентный MSW-тест отдельно проверяет отображение details сервера, даже если локальные
   ограничения формы уже прошли. Для цены текст API: «Цена должна быть больше 0».
10. **429 и независимость.** Это лимит ЛР11, а не случайная ошибка пароля. Свежая изолированная
    среда и ограниченный набор входов сохраняют реальное поведение лимитера. Нельзя просто
    отключить защиту production ради тестов. В серверных unit/integration тестах пропуск
    лимитера при NODE_ENV=test отдельно перекрывается тестами настоящего ограничения.
11. **Build и защита main.** Build проверяет сборку импортов/ресурсов. Обязательные status checks
    блокируют merge при красном job; обход администратором ломает гарантию проверенного main.
12. **Только CI падает.** Возможны разный Node/lock-файл, регистр пути на Linux, отсутствующие
    переменные или зависимости от порядка/тайминга. Сначала смотреть конкретный лог/trace,
    сверить версии и env, воспроизвести через npm ci и убрать зависимости между тестами.
13. **ИИ.** Да, Codex использован для миграции на MSW, страниц/форм, E2E, конфигурации CI,
    проверки экспериментов и документации. Приведены реальные локальные замеры;
    облачные проверки отмечены как невыполненные.
